## COMPLETED — and the answer to requirement 7

**v34 can do this with no app-code change.** The app blob on this branch is
byte-identical to `main` (`9399d78f…`). The correction is entirely in data.

`upsertShow` layers every key of `op.show` onto the record — on create, over the
`buildPlannedShow` scaffold; on update, over the matched record. So the passed
fields (`passed`, `passedReason`, `passedRevisit`, `passedAt`, `passedSource`)
can be carried directly by the package. Verified against v34 on all four paths:

| Board state | Result |
|---|---|
| Party **absent** | CREATE, `passed:true`, not missed, not upcoming, $450 booth preserved, **0 payments** |
| Party **pending** | UPDATE in place, same record id, now passed, leaves Pending / Applied |
| Party **already passed** | 0 changes |
| Same name + date, **wrong town** | **BLOCKED**, record byte-for-byte untouched, no duplicate created |

### ⚠️ One invariant IS bypassed, and Scout should decide about it

`pndMarkPassed()` refuses to pass a `completed` or `active` show — *"a worked
show is history, not a decision."* An `upsertShow` writing `passed:true`
**does not go through that guard**. Measured on v34:

```
pndMarkPassed on a completed show  -> returns false, passed stays false
upsertShow    on a completed show  -> passed becomes true
                                      status stays 'completed'
                                      record then appears in BOTH tabs
```

**Why I shipped it anyway, rather than changing app code:**

- Requirement 7 asked me to stop and explain *before* changing app code, and the
  data-only route was the stated preference. So this is the explanation, not a
  silent decision.
- The bypass is not reachable for this package on this board. Party is absent
  from both copies (Scout verified), so the create path runs. Its date,
  2026-09-19, is in the future, so it cannot legitimately be `completed`.
- The consequence if it ever were reached is bounded and visible: the record
  would show in both Completed and Passed. Financials are untouched — `calcYTD`
  keys on `status==='completed'`, not on `passed` — and Restore reverses it.
- The preview would show it as an UPDATE listing `passed: false → true`, so a
  human reading the preview sees it before anything is written.

**What a v35 would add**, if Scout wants the hole closed: a `requireStatus` /
`refuseStatus` constraint on the matcher, or a `passedState` operation that
routes through `pndMarkPassed()` so the guard applies. Both are app changes and
neither is in this branch.

### Two deliberate departures from the canonical seed

Both are recorded in the package under `seedDepartures`.

1. **The projected $4 ramp-parking `showExpense` is omitted.** `calcYTD` adds a
   non-completed show's `showExpenses` to YTD spend regardless of passed state —
   measured directly: a passed show carrying it reports $4 of spend, without it
   $0. Including it would book money we will never spend on a show we are not
   attending. The parking facts survive verbatim in the notes ("PARKING $4 all
   day: Lake Ave Ramp…"). *This is arguably an app-level bug — a passed show's
   projected expenses should not count as spend — and is worth a v35 look.*
2. **Per-day `openTime`/`closeTime` are not set**, because a package's `show`
   object cannot reach into `days[]`. Verified equivalent: `dayCallClose()`
   falls back to the show-level times, and the created record reports identical
   hours (call 11 AM, open 12 PM, close 7 PM) and identical `showHours` (8).

Everything else is the app's own `pop_racine_20260818` seed: `Racine, WI`,
2026-09-19, 1 day, $450 booth, 24 miles, `confirmed:false`,
`depositDue:'2026-08-22'`, 12:00–19:00, hours verified, and all 1,176
characters of the seed notes — extracted from the running seed, not retyped.
**No `boothPayments`:** the show was never approved and never paid.

## DECISIONS

1. **`upsertShow`, not `upsertShow` + `markPassed`.** A two-operation form would
   route the passed state through the proper guard, but `pkgPlan` plans every
   operation against the *original* state, so on a board where Party is absent
   the second operation would preview as UNMATCHED while actually passing the
   record at execute time. A preview that understates what will happen defeats
   the whole point of the preview. One honest operation beats two with a lying
   preview.
2. **Matched by `nameContains` + exact date + Racine evidence**, with
   `keepExistingName` — the Last Fling lesson applied pre-emptively. If the
   record exists under a drifted name it is updated, not duplicated; if a
   same-named show sits elsewhere it is refused.
3. **`passedAt` is a fixed `2026-08-26T00:00:00.000Z`.** A package cannot call
   `new Date()`. This is the date the decision was packaged, and it is stable
   across reapplies — which is what makes "reapply changes nothing" true.
4. **`depositDue` kept.** It is the factual application deadline and it is
   history. Verified it raises no payment-due alert while passed.
