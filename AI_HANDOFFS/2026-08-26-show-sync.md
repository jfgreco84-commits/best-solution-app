## COMPLETED

### 1. Passed / Not Doing — a stored, reversible show state

Four fields on a show record, set together and removed together:

| Field | Meaning |
|---|---|
| `passed` | `true`. The only value that counts — a truthy string does not. |
| `passedReason` | Why, in the owner's words. Required by the UI. |
| `passedAt` | ISO timestamp the decision was recorded. |
| `passedRevisit` | Optional follow-up for the next application cycle. |
| `passedSource` | `'manual'`, or the `packageId` that set it. |

`isPassed(sh)` is the single predicate. `isMissed()` returns false for a passed
show **before** its date test, so a passed record can never drift into the
Missed tab once its date goes by — that was the specific requirement, and it is
enforced at the lowest level rather than in each view.

**Removed from** (each verified): Upcoming, all three Booking Pipeline buckets
and `oweTotal`, `depositAlerts()`, `calcBoothTally()` owed/due/confirmed counts,
`secBooth()` committed/owed, booked show + show-day + staffed-hour counts,
`rCalendar()` month grid, `exportCalICS()`, `showConflicts()`,
`transferableShows()`, and the pack-inventory action on the show page.

**Deliberately NOT removed:** money already spent. If a booth deposit was paid
before the decision, that cash left the account, and it stays in `calcYTD()`
expenses, in the P&L, and in the booth tally's `paid` figure. `secBooth()` grows
a sunk-cost line naming the amount so it is visible rather than silently folded
in. Dropping it would make the books lie in the owner's favour, which is the one
direction an accounting bug must never go.

**Reversible:** `pndRestore()` deletes exactly the fields `pndMarkPassed()`
added, so a restore returns the record to its previous shape byte for byte —
asserted in the tests and confirmed in the browser.

**Refusals:** a `completed` or `active` show cannot be passed, from either the
UI or a package. A show that was actually worked is history, not a decision.

**UI:** a "🚫 Passed / Not Doing (n)" tab on Shows with an explanatory banner;
an orange PASSED badge that wins over every other badge; a card block showing
the reason, the revisit note, when it was recorded, any sunk booth cost, and a
Restore button; "🚫 Mark Passed / Not Doing" on the show detail page, which
opens a modal that **requires a reason** before it will proceed.

### 2. Apply Show Update Package

New Settings card: **📦 Apply Show Update Package**. Paste or choose a JSON
file, get a full preview, tick one confirmation box, apply.

Against the twelve stated requirements:

1. **Authenticated only through the normal app session.** The feature contains
   no auth code. It reads `_cloudUser`, which the existing Sign In screen sets.
2. **No password touched.** It never asks for, stores, reads or transmits one.
3. **Publishable key + existing RLS.** It creates no Supabase client of its own
   and adds no second authentication path; it calls the app's existing
   `cloudPull()` / `cloudPush()` under the session already established.
4. **Versioned JSON, file or paste.** `format` + `version` are hard gates.
5. **Full preview before writing:** per operation — CREATE / UPDATE / MARK
   PASSED / NO CHANGE, the matched record with its id, *how* it matched, every
   changed field with before and after, duplicate-payment warnings, ambiguous
   matches, and unmatched records.
6. **One explicit confirmation.** A checkbox plus the Apply button; `pkgApply()`
   refuses if the box is not ticked (verified).
7. **Existing save path.** It mutates `S` and calls `saveS()` — localStorage
   then the owner's own session. It then cancels the debounced push and
   **awaits** the real `cloudPush()` so the result can be reported. Same client,
   same session, same table as every other button in the app.
8. **Idempotency key.** `packageId` is recorded in `S._pkgApplied` on success
   and a second apply is refused outright.
9. **No duplicate payments.** A payment is the same payment when it is the same
   money on the same day. Note text is deliberately not part of the test, so
   re-wording a note cannot sneak a duplicate through.
10. **Backup.** The preview screen carries a Download Backup File button above
    the Apply control.
11. **After-apply verification report.** Reports **three separate outcomes** —
    local verification, cloud write, cloud verification — and never collapses
    them. The third is a fresh read back from the server. Downloadable as JSON.
12. **No RLS weakening, no service-role bypass.** None exists in the code.

Beyond the requirements, because a `packageId` can go missing exactly the way a
migration marker did in the 2026-08-20 replay, **every operation is
independently self-checking**: a create becomes a match when the show already
exists, a final duplicate refusal sits inside the create path itself, and
marking an already-passed show is a no-op. There is also a **dry run**: the
whole package is applied to a deep clone and re-planned there first, and if it
does not settle, the real state is never touched.

**Matching logic, exactly:**

- Names are normalised with `mrgNormName()` — the same function the replay guard
  uses. It folds en dash, em dash, non-breaking hyphen and minus to `-`, drops
  punctuation, collapses whitespace, lowercases. `Sip & Sleigh — Carol Stream`
  and `sip sleigh - carol stream` are the same show.
- **Primary:** normalised name **and** `startDate` both equal. Exactly one hit
  wins.
- **Secondary:** normalised name alone. Accepted only when unique, and reported
  as a **DATE DRIFT** warning showing both dates, because later migrations
  legitimately move seeded dates.
- **Two or more candidates is never resolved by guessing.** The operation is
  BLOCKED, the whole package becomes unapplyable, and the candidates are listed.
- **Sweep operations** (`nameContains`) list every matched record individually
  by name and date in the preview, and take an `expectMax`. More matches than
  expected blocks the operation, so a broad name rule cannot quietly sweep up an
  unrelated show.
- An optional `location` filter narrows a sweep by normalised substring.

## Scout round 2 — the three corrections

### 1. Authentication is required, and enforced twice

Applying a package is a cloud operation, not a local one. A change that lands
only on this device is not saved — it is a divergence waiting to be overwritten
by the next sync from another device. So `pkgGate()` now requires **all four**:

| Condition | Why it is separate |
|---|---|
| Supabase client present | Without it there is no path to the account at all. |
| `_cloudUser` set | The write must go through Justin's own session. |
| `navigator.onLine !== false` | A signed-in session on a plane passes the auth check, writes locally, fails the push, and leaves the owner believing the cloud has it. |
| `_syncState === 'synced'` | A device mid-sync does not yet agree with the server. |

Loading and previewing while signed out is still allowed — previewing changes
nothing. What is blocked is Apply. The button and the checkbox are **absent**,
with the specific reason named and an explicit note that the package itself is
fine. And `pkgApply()` re-tests `pkgGate()` itself as its first act, so calling
it directly from anywhere refuses identically. The disabled button is a
courtesy; the function is the enforcement.

### 2. Fresh cloud preflight, awaited push, real cloud verification

`pkgApply()` is now `async`. The order is deliberate:

1. **Gate** (above). Nothing has happened.
2. **Dry run** on a deep clone; must settle. Nothing has happened.
3. **Fresh `cloudPull()`** — taken *now*, as the last act before any mutation.
   A green dot proves the last push worked; it says nothing about what another
   device has written since.
   - `pkgCloudDivergence()` compares `_updatedAt` **and** an
     order-independent fingerprint. `_updatedAt` catches the ordinary case; the
     fingerprint catches equal-or-missing timestamps over different content,
     which `_updatedAt` alone cannot see. The fingerprint is built on
     `p2bCanon()`, not `JSON.stringify`, because Supabase returns jsonb with
     keys reordered and a plain stringify would report a false difference.
   - Cloud newer, or materially different, or unreadable → **abort with zero
     local changes**, and tell Justin to reload and re-apply from a synced
     device.
4. **Mutate locally**, save, verify locally.
5. **`clearTimeout(_cloudTimer)` then `await cloudPush()`** — the debounced
   push `saveS()` queued is cancelled so this is the single write and its result
   is the one reported. `cloudPush()` now returns `{ok,reason,error}`; its
   existing callers ignore the return and behave exactly as before.
6. **Second fresh `cloudPull()`**, and verify against *the document the server
   hands back* — not the object we sent.

`pkgVerifyCloud()` checks, each reported by name so a partial success cannot be
rounded up to a pass: the document is readable; the `packageId` marker is
present; re-planning the package against the cloud copy settles to zero;
per-operation, each created record is present with its payments and **no
duplicates**; each `markPassed` target really is passed; and the **Wonderful
World of Weddings record is byte-for-byte identical** to its pre-write state.

The report now shows three separate outcomes and never collapses them:

```
1 · Local verification passed    YES/NO
2 · Cloud write completed        YES/NO
3 · Cloud verification passed    YES/NO
     UPDATE COMPLETE             YES/NO
```

Anything short of all three renders **LOCAL CHANGE APPLIED / CLOUD UNVERIFIED**
in red, with recovery instructions and an explicit warning not to apply the
package on another device. A settled local re-plan on its own is the weakest of
the three signals — it only says the device agrees with itself — and is never
presented as success.

No RLS change, no secret key, no second authentication path, no second Supabase
client.

### 3. Rustic Fox matching requires the organizer or location

`expectMax` caps how many records a sweep may touch. It says nothing about
whether they belong to the sender. "Kris Kringle" is a generic Christmas-market
name that any organizer in the Midwest might use.

`requiredEvidenceAny` is that missing proof: every candidate must **also** carry
one of the given strings in a structured field. The shipped package now splits
the cancellation into two strictly-constrained operations:

| Operation | `requiredEvidenceAny` | `expectMax` |
|---|---|---|
| Rustic Fox — North Aurora | `north aurora`, `rustic fox`, `fox found` | 3 |
| Rustic Fox — Carol Stream | `carol stream`, `rustic fox` | 3 |
| Party on the Pavement | `racine` | 1 |

A record whose name matches but whose location/organizer does not identify it is
**excluded and reported by name and date** in the preview — "we considered this
and deliberately left it alone" is information the owner needs in order to trust
the sweep. For a single-record `upsertShow` the same situation **fails closed
and blocks**, rather than creating a near-duplicate beside a record it declined
to touch.

Against the real seeded board this resolves exactly as intended: the North
Aurora operation takes the two North Aurora shows and reports leaving the two
Carol Stream ones alone; the Carol Stream operation does the mirror. All four
end up passed, each via an operation that proved whose show it was. (The
preview is a little repetitive as a result — each operation lists the other's
targets under NOT TOUCHED. That is honest, and the alternative is showing less
than what happened.)

## What the corrections caught

Two real bugs in my own round-1 code, neither visible without the tests Scout
asked for. Both are fixed and both now have regression tests.

**1. Notes were treated as identifying evidence, and prose negates.**
My first implementation searched `location`, `organizer` **and** `notes` for the
evidence strings. The negative test Scout asked for — an unrelated "Kris Kringle"
at another organizer — failed on the first run, because its note read:

> "Run by the Oconomowoc Chamber. **Nothing to do with The Rustic Fox.**"

That contains `rustic fox` and satisfied a substring test exactly as well as a
note saying it *was* a Rustic Fox show. The constraint would have swept up the
precise record it existed to protect. **Notes are no longer searched at all.** A
substring test can only be trusted against a field whose whole value *is* the
identifier; `location` and `organizer` are those fields, prose is not. Two tests
now pin this: a negating note is not evidence, and a *confirming* note is not
evidence either.

**2. `pkgPlan()` was documented read-only and was not.**
It called a helper that lazily initialised `state._pkgApplied = {}` — so merely
*previewing* a package added a field to the live state. With the new pre-write
cloud check in place this was fatal: the preview dirtied the local document, the
preflight compared it against a clean cloud copy, saw a 17-character difference,
and aborted. **Every apply would have failed as a false divergence, forever.**
The happy-path scenario caught it on its first run. `pkgAppliedRead()` (never
writes, used by planning) is now split from `pkgAppliedEnsure()` (writes, used
only at commit). A test asserts that planning mutates the state literally not at
all.

## DECISIONS

1. **Money spent stays spent.** The single most consequential call here. See
   above — passed shows leave every forward-looking total but remain in the
   real-money math, with a visible sunk-cost line.

2. **`isMissed()` excludes passed at the top, not per-view.** One line, and it
   makes "do not label it Missed" true everywhere by construction, including in
   code written later.

3. **Payment method was left blank on both new shows.** The sheet says
   "Not documented. Do not invent one." So there is no method field on either
   payment; instead each payment note and each show's notes say plainly that the
   method is undocumented and needs confirming. Nothing was inferred.

4. **`Rustic Fox 2026` sweep uses `expectMax: 6` against a known set of 4.**
   Enough headroom for a name variant that exists on the live device but not in
   my fixture, low enough that a genuinely over-broad match blocks instead of
   sweeping. The real protection is that the preview names all four matched
   records individually, so an unrelated show would be visible before applying.

5. **Mileage was omitted on the replacement Rustic Fox market** — the sheet does
   not carry it. The show's notes say so and tell the owner to set it in Edit
   Show before relying on gas or IRS mileage figures. A guessed number would
   silently corrupt the mileage deduction.

6. **`APP_VERSION` v32 → v33.** App behaviour changed, which is exactly the
   documented trigger for advancing it.

7. **The package is a data change, not a migration.** No seed was added to the
   HTML. The repo's own replay-guard documentation is explicit that seeding
   shows through a migration is how duplicate identities got minted on
   2026-08-20, and the owner's instruction was not to patch HTML to make the
   interface merely look updated.

## NOTES FOR WHOEVER PICKS THIS UP

- **Phase 2B will now abort if anyone runs it after a package is applied.**
  `S._pkgApplied` is a state field the P2B manifest does not authorise, so the
  "Review what the cloud is missing" flow will see an unauthorised field and
  refuse. P2B was a completed one-time operation pinned to fingerprint
  `bb3ca777/86919`, which no longer matches anyway, so it was already going to
  abort — but the failure will now name a different cause. This is
  fail-safe (it changes nothing) rather than a bug, and is recorded here so
  nobody debugs it twice.
- **This repository is public.** The package carries booth costs, payment dates,
  organizer names and venue addresses. That is consistent with what the app file
  already contains — the Wonderful World of Weddings seed carries an invoice
  number, a card last-four and organizer contact details — but it is worth a
  deliberate decision rather than drift. Separately, the pre-existing card
  last-four in that seed is worth removing on its own merits.
