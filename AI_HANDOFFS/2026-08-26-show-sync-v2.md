## COMPLETED

### Why v1 missed

`mrgNormName("The Last Fling Artisan Market")` is `"the last fling artisan
market"`. The package named `"The Last Fling"` → `"the last fling"`. Those are
not equal, so:

- the **exact** name+date match found nothing,
- the **name-only** fallback found nothing,
- `pkgResolve` returned `mode: 'none'`,
- and `'none'` on an `upsertShow` means **create**.

The last-line duplicate refusal inside `pkgExecute` compared normalized names
for *equality* too, so it would not have caught it either. Two independent
guards, both blind to the same drift.

### The v2 package

| | v1 | v2 |
|---|---|---|
| `packageId` | `…_v1` | **`pkg_2026-08-26_show-sync_v2`** |
| Last Fling match | `name` + `startDate` (exact) | `nameContains ["last fling"]` **AND** `startDate 2026-08-30` **AND** `requiredEvidenceAny ["valley ridge","antioch"]` |
| Last Fling action | **CREATE** (duplicate) | **UPDATE** the existing record |
| Name handling | would write `"The Last Fling"` | `keepExistingName: true` — the organizer's own name is preserved |
| Other five operations | — | byte-for-byte unchanged |

All three conditions must agree, which is what satisfies the "different Last
Fling stays untouched" requirement in both directions: a wrong date fails the
`startDate` test, a wrong venue fails the evidence test.

`keepExistingName` was deliberate. The sheet's shorter "The Last Fling" is a
label; "The Last Fling Artisan Market" is what the organizer actually calls it
and what is already in the books. Renaming a live record to match a spreadsheet
abbreviation loses information for no gain.

### Three matcher fixes in the app (hence v34)

1. **`nameContains` now honours `startDate`.** A fragment like "last fling"
   otherwise reaches every year's instance of a recurring event. It stays
   optional, because a cancellation sweep legitimately spans several dates.
   Records the fragment reached but the date excluded are reported as
   `NOT TOUCHED` rather than silently dropped.

2. **Near-duplicate detection — `pkgNearDuplicates()`.** On the same start
   date, one normalized name containing the other is treated as the same event,
   and a create is refused: blocked at plan time with the existing record named,
   and refused again inside `pkgExecute` as the last line. Show names drift —
   an organizer adds "Artisan Market", a sheet abbreviates — but the date does
   not. Deliberately blunt: two genuinely different shows on one date where one
   name contains the other are blocked too, and being told to look is the right
   outcome, because a silent duplicate in the books is far worse than a stopped
   package.

3. **An `upsertShow` matching more than one record now blocks.** Previously
   `ambiguous` only covered the name/date selectors; a `nameContains` selector
   returning several had `hits[0]` picked for it silently. Writing a package's
   fields into whichever record sorts first is never right.

Cloud verification also gained a **no duplicate in cloud** check per upsert, so
a duplicate that somehow reached the server would fail verification instead of
being reported as success.

## DECISIONS

1. **v1 was left in the repo, not deleted.** It is the evidence for why v2
   exists, and section 10 of the suite runs it against the real board to prove
   the defect was real. It is now blocked by the near-duplicate guard, so it
   cannot be applied by accident.

2. **The fix went into the matcher, not just the package.** A package edit alone
   would have fixed this one record and left the next drifted name to fail the
   same way. The requirement itself — "match only when all appropriate evidence
   agrees" — needed `startDate` support on `nameContains`, which did not exist.

3. **Near-duplicate detection keys on the date, not on name similarity
   scoring.** Fuzzy name matching invites false positives on a business's real
   books. Same-date plus a containment relationship is narrow, explainable, and
   would have caught this exact bug.

4. **App version bumped to v34.** Behaviour changed, which is the documented
   trigger. This matters practically: **v2 must not be applied against the
   deployed v33 build**, which does not honour `startDate` on a `nameContains`
   selector.

### A third real bug, caught by the decoy tests

`pkgResolve`'s contains branch returned `mode: 'contains'` even when every
candidate had been filtered out, so the upsert branch — which tested
`mode === 'none'` — went looking for `hits[0]` and threw on an undefined
record. It surfaced on the first run of the wrong-date decoy. Fixed twice: the
resolver now reports `'none'` when nothing survives, and the upsert branch keys
on the hit **count** rather than the mode string, so a future resolver change
cannot turn into a crash.
